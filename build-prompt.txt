# PROJECT: AI JOB SEARCH & MATCHING SAAS

## 1. Product context and objective

We are building an AI-powered job-search platform that helps users discover relevant job opportunities based on their professional profile, CV, skills, and job preferences.

Users will interact with the platform through two connected interfaces:

1. A web-based SaaS dashboard.
2. Their own Telegram bot, which they create through Telegram’s BotFather and connect to their SaaS account.

The platform provides the underlying job-search and matching infrastructure. Users should not need to manage API credentials for Adzuna or OpenAI, write code, or configure webhooks.

The initial job data provider is **Adzuna**. OpenAI will be used to evaluate job relevance and match listings to the user’s profile.

The intended stack is:

* Next.js for the web application and server-side functionality.
* Supabase for authentication, PostgreSQL, and file storage.
* Vercel for hosting.
* Telegram Bot API for bot connections and interactions.
* Adzuna for job listings.
* OpenAI for AI-based job matching.

Inspect the existing repository and use its current structure, framework conventions, dependencies, and design system where appropriate. Do not blindly replace existing work.

### The intended outcome

A user should be able to:

* Create an account and sign in.
* Set up their professional profile.
* Upload and manage their CV.
* Define job-search preferences.
* Search for jobs and receive relevant results.
* Save jobs and revisit previous matches.
* Connect their own Telegram bot.
* Search for jobs through that bot.
* View and manage credits.
* Buy credit packs.
* Subscribe when a subscription plan is configured.

The dashboard and Telegram bot must share the same account, profile, preferences, saved jobs, match history, and credit balances.

This is a focused job-search product. It is not a generic chatbot, a job-posting marketplace, or a general-purpose Telegram bot builder.

# 3. Credit system and business model

The credit system is a core part of the product. Implement it carefully and enforce it on the server.

## Free users

A free user receives:

**5 credits per day.**

One credit represents one job successfully delivered to the user.

Daily free credits:

* Reset daily.
* Do not roll over.
* Must not be repeatedly granted because a user refreshes the page or changes devices.

## Subscribers

A subscription replaces the standard five-credit free daily allowance.

Subscribers receive the daily allowance defined by their subscription plan.

Unused daily subscription allowance does not roll over.

Subscription prices and allowances are not finalized, so make them configurable. Do not invent a successful subscription purchase when no billing provider is configured.

When a subscription expires or is cancelled, apply the appropriate entitlement based on the actual subscription status.

## Purchased credit packs

Implement these initial credit packs:

| Pack     |  Price | Credits |
| -------- | -----: | ------: |
| Starter  | ₦1,000 |       5 |
| Standard | ₦3,000 |      20 |
| Large    | ₦5,000 |      40 |

These are the initial product values. Prices and credit quantities should be stored as configurable product records rather than scattered hardcoded values.

Purchased credits:

* Remain available until used.
* Do not expire at the daily reset.
* Must be tracked separately from daily allowance credits.

## Credit consumption rules

* One credit is deducted per job successfully delivered.
* Do not charge for listings merely retrieved from Adzuna.
* Do not charge for candidates evaluated internally by OpenAI.
* Do not charge for failed searches.
* Do not charge for jobs that were not delivered.
* If fewer suitable jobs are found than requested, charge only for the jobs actually delivered.
* If no suitable jobs are found, do not deduct credits.
* A failed integration must not cause an accidental deduction.
* Prevent duplicate charges from repeated clicks, concurrent requests, retries, or duplicate Telegram updates.

The backend must be the source of truth for balances and entitlements. Never trust a credit balance, price, subscription status, or credit quantity supplied by the browser.

Track daily allowance grants, purchased credits, spending, and adjustments through an auditable ledger or equivalent transaction model.

Use atomic database operations, transactions, or suitable Postgres RPC functions to prevent race conditions and double spending.

### Credit source priority

Implement a consistent, documented spending order. A sensible default is to consume the expiring daily allowance first, then purchased credits. Keep the accounting clear so the user can see the distinction.

# 4. Job-search experience

The platform should let users search for jobs using their saved preferences.

A search should follow this general process:

1. Validate the search request.
2. Check the user’s account, credits, and plan limits.
3. Determine how many jobs the user wants returned.
4. Construct a suitable Adzuna query.
5. Retrieve a bounded set of candidate listings.
6. Normalize and deduplicate the candidates.
7. Apply inexpensive deterministic filters.
8. Evaluate relevant candidates with OpenAI.
9. Rank qualifying jobs.
10. Deliver the requested number where possible.
11. Persist the search and delivered matches.
12. Deduct credits only for jobs successfully delivered.

The system must not retrieve an arbitrary number of listings and discard most of them without considering provider usage and AI costs.

However, it may need to evaluate more candidates than the number ultimately delivered. Make this a controlled, bounded process.

## Search quantity selection

Users should choose how many jobs they want returned.

Offer configurable choices such as:

* 3 jobs.
* 5 jobs.
* 10 jobs.

Only show quantities permitted by the user’s available credits and plan limits.

If a user has insufficient credits for a requested quantity, offer an affordable option or a clear path to purchase more credits.

The user should understand how many credits the requested search may consume before starting it.

Do not charge for internal candidate listings. Charge only for jobs delivered.

## Search results

Each result should display, where available:

* Job title.
* Company.
* Location.
* Work arrangement.
* Employment type.
* Salary information.
* Posting date.
* Concise description or summary.
* AI relevance explanation.
* Original listing link.

Use the provider-supplied original listing URL where available.

Do not fabricate job listings, salaries, employers, or descriptions.

Make it clear that listings originate from external sources and that users should verify details on the original listing.

Do not describe an AI relevance score as a probability of getting hired or a guarantee of suitability.

# 5. Adzuna integration

Adzuna is the initial job data provider.

Keep the integration in a server-only provider module. Credentials must never be exposed to client-side code.

The API documentation supplied for this project identifies the following endpoint pattern:

`https://api.adzuna.com/v1/api/jobs/{country}/search/{page}`

The supplied documentation lists parameters including:

* `results_per_page`
* `what`
* `what_and`
* `what_phrase`
* `what_or`
* `what_exclude`
* `title_only`
* `where`
* `distance`
* `location0` through `location7`
* `max_days_old`
* `category`
* `sort_dir`
* `sort_by`
* `salary_min`
* `salary_max`
* `salary_include_unknown`
* `full_time`
* `part_time`
* `contract`
* `permanent`
* `company`

**Verify the current official Adzuna documentation before implementing the adapter.** Confirm authentication, parameter names, response fields, supported countries, limits, and applicable usage terms.

Do not assume Nigeria is supported merely because the product is intended for Nigerian users. Handle unsupported countries gracefully and clearly communicate which locations are currently supported.

Do not promise remote-job coverage unless it is verified.

## Candidate retrieval and internal usage controls

Implement:

* Bounded candidate retrieval.
* Pagination only when justified.
* Deduplication by provider and provider job ID, with a fallback fingerprint if necessary.
* Rate limiting.
* Backoff for transient provider failures.
* Handling for provider quota exhaustion.
* Configurable candidate limits.
* Configurable AI evaluation limits.
* Caching only where appropriate and permitted by Adzuna’s terms.

Adzuna’s documented response may contain only a snippet of the job description. Do not assume a complete job description is available.

Preserve any source attribution required by the provider’s terms.

Keep provider-specific logic isolated so another provider can potentially be added later without rewriting the entire application.

# 6. OpenAI job matching

Use OpenAI to evaluate how relevant a job is to the user’s profile and preferences.

The model should consider available information such as:

* Target role and keywords.
* Skills.
* Professional experience.
* Experience level.
* Location and work arrangement.
* Employment type.
* CV-derived information, if CV parsing is actually implemented.
* Available job title, company, description, and other listing fields.

Use a low-cost model configurable through an environment variable.

Do not hardcode a model choice throughout the application.

## Matching pipeline

Use inexpensive deterministic filtering before invoking the model.

Then:

* Send only the candidate data necessary for evaluation.
* Request structured output.
* Validate the response against a schema.
* Reject malformed or unusable responses safely.
* Rank qualifying jobs.
* Return concise, evidence-based explanations.

Treat job listing text as untrusted input. The model must not follow instructions embedded in job descriptions or other external listing content.

Make the relevance threshold and candidate-evaluation limits configurable.

Handle OpenAI rate limits, errors, timeouts, and malformed responses gracefully.

The matching service must not claim certainty or guarantee that the user will get an interview or job.

# 7. Telegram bot integration

Telegram integration is a major feature of the product.

## One user, one bot

For the MVP:

**One SaaS account can connect one Telegram bot.**

Users create their own bots using Telegram’s BotFather.

They then paste the BotFather token into the SaaS dashboard.

The platform handles the connection and configuration.

Users should not need to:

* Write bot code.
* Configure webhooks manually.
* Supply Adzuna credentials.
* Supply OpenAI credentials.
* Manage the platform’s internal job-search infrastructure.

## Connection flow

Implement this flow:

1. User opens Telegram Integration in the dashboard.
2. The UI explains how to create a bot using BotFather.
3. User pastes their bot token.
4. The server validates the token using Telegram’s `getMe` method.
5. The server checks that the bot is not already connected to another account.
6. The server securely stores the token.
7. The server associates the bot with the authenticated SaaS user.
8. The server registers the webhook.
9. The dashboard displays the actual connection status and bot username.
10. The user can disconnect or replace the bot.

Do not show a successful connection state unless Telegram confirms it.

## Token security

Bot tokens are sensitive credentials.

* Never expose a stored token to the browser after submission.
* Never place tokens in client-side code.
* Never log tokens.
* Encrypt tokens at rest using a server-side encryption key or another appropriate secure secret-storage mechanism.
* Keep encryption keys in environment configuration.
* Validate and sanitize all token-management requests.
* Prevent one bot token from being associated with multiple accounts.
* Handle token replacement and disconnection safely.
* Document the implications of encryption-key rotation.

Do not use the bot token as the sole authorization mechanism for unrelated user data. Every incoming bot update must be mapped to the correct connected bot and SaaS account.

## Webhook architecture

Use Telegram webhooks for production rather than requiring a continuously running polling process.

Implement a secure webhook route that:

* Validates Telegram’s webhook secret token through the `X-Telegram-Bot-Api-Secret-Token` header.
* Resolves the correct connected bot and account.
* Handles messages and callback queries defensively.
* Acknowledges callback queries promptly.
* Handles duplicate updates idempotently.
* Avoids duplicate credit deductions.
* Avoids unbounded AI work inside a webhook request.
* Uses a suitable background-processing approach if supported by the project and hosting environment.
* Otherwise uses bounded processing with clear timeout and retry behaviour.
* Does not leak one user’s data to another user.

The platform should respond promptly to Telegram. If a job search takes time, acknowledge the interaction, show a working message, and then deliver results.

Document any remaining limitations related to serverless execution, queues, retries, or processing time.
